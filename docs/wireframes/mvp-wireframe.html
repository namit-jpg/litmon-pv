Build notes
Changed Ops page becomes two things

Today OpsPage.tsx shows infra metrics and background jobs. That stays as an admin screen; this business dashboard is separate and is what the PV user opens first.

New Every tile drills through

Each tile is a link into the workspace pre-filtered to that metric. Requested explicitly in step 12 and the main thing that stops a dashboard being decoration.

New Search-completion surface

SearchRun already records status and errors. Nothing currently tells a user that a product has gone unmonitored — two of the eight alert triggers depend on it.

Exists Counts are already queryable

/api/queues/stats and /api/sla/overdue cover part of this. The funnel needs classification counts that the new taxonomy introduces.

Changed Folders replace severity tabs

Current tabs are Expedited / Priority / Standard / QC — triage severity. Step 9 asks for workflow state. Severity moves to the Pri column and to sort order, which is where it belongs.

New Ten filters

/api/articles currently filters on queue, status and open-only. Product, ingredient, source, classification, signal status, submission status, assignee and priority all need adding.

New Priority is not SLA

There is no priority field today — urgency is inferred from sla_due_at. Alert priority definitions are still to be supplied by the partner.

Open Who owns what

One user for everything, one per product, or a primary plus backup? Drives whether the Assigned filter is a convenience or load-balancing.

Changed Nine classifications, not two

ArticleStatus ends at disposition_not_case / disposition_valid_icsr. Step 4 needs nine values, and classification has to separate from workflow status — they are conflated in one enum today.

New Extraction becomes typed columns

Indication, dosage, outcome, country, reporter type and excerpts live in a loose entities JSON blob on ScreeningResult. Step 5 lists ~18 fields that need real columns to be filterable and validatable.

New Signal tags are a separate layer

Fourteen tags, multi-select, distinct from classification and from the review decision. Confirmed signal is gated to PV lead.

Changed Nine decisions, not six

DecisionAction is ICSR-shaped. Step 10 adds mark-invalid, mark-duplicate, not-relevant, prepare-for-submission, retain-internally and close.

Exists ICSR checklist and audit

The four validity checkboxes, rationale capture and per-article audit already work in ArticlePage.tsx — they fold into this screen rather than being rebuilt.

New The report is the artefact

Step 11 wants a standing document, not a review form. Same screen, but it must render and export as a report for a file or an inspector.

Exists The plumbing is real

notifications.py logs and can send SMTP. It is wired to exactly one trigger — SLA breach — and surfaced as one button on Ops.

New Seven more triggers

Signal detected, serious result, processing failure, awaiting review, deadline approaching, unresolved past review period, search failed, no search in period.

New Alerts need to be records

There is no alert entity — events are logged and gone. Read state, priority, recipient and channel all need persisting for this inbox to exist.

Open Which channels for the pilot

In-app and email are recommended and shown as on. The rest are drawn as later-phase so the partner can see the ask was heard without it entering scope.

Open The CDSCO schema is not known

No XML generation exists anywhere in the codebase — the only XML is PubMed EFetch parsing. Schema, mandatory fields, validation rules, a sample accepted file and the acknowledgement format are all still needed.

Exists Field extraction is half-built

export_service.py already emits patient, product, event, seriousness, listedness, reviewer and decision as JSON and CSV. That is the input the XML mapping would consume.

New Blocking validation

Generation must refuse while a mandatory field is missing, and name what is missing. The rules cannot be written until the specification arrives — the mechanism can.

New Version store and submission record

ExportPackage stores payloads but has no version chain, no submit/store decision and no gateway reference.

Open Which gateway

CDSCO portal, PvPI, the manufacturer's own safety system, or a third-party platform. Left as an unset dropdown rather than guessed.

Exists Largely built

AuditEvent and AuditPage.tsx cover actor, action, entity, payload and timestamp.

Changed New event types

Alerts, classification changes, signal tagging, regulatory generation and submission recording all need to write events.

New Exportable log

Inspection readiness is a stated selling point, so the log needs to leave the screen.

Changed Six fields to add

Product has name, inn, brands, synonyms and atc_code. Step 1 also needs MAH, markets, monitoring frequency, responsible reviewer, and a real split between generic name, active ingredient and API.

New Ingredient is not the same as API

The feedback lists them separately. For a combination product like amoxicillin with clavulanate the distinction stops being academic.

Exists Synonyms already drive the query

Versioned search strings with PV lead approval are already implemented — that governance carries straight over.

Open The four products

Brand names here are placeholders. The real four, with synonyms, are on the partner's input list.

New Sources become configurable

PubMed is hardcoded in services/pubmed/. No source entity exists. Adding one now is what makes step 2's "additional sources later" cheap rather than a rewrite.

New The PubMed / NLM / NCBI distinction, shown

Modelled as source versus provider rather than three checkboxes. The feedback calls this out specifically as something the design must get right.

Exists Connection health

Rate limiting, retry and E-utilities config are already in core/config.py and the PubMed client — they just have no UI.

Changed Schedule per product

workers/scheduled_search.py exists but frequency is not a product attribute and there is no schedule view. Step 3 says the user should never run a search by hand.

Exists Run history is complete

SearchRun already records hits, new, re-hits, query snapshot, error and a response hash. SearchRunPage.tsx shows it.

New Exception queue

Holds anything that could not be processed and alerts on it. Deliberately keeps causes separate rather than collapsing them into one invalid bucket.

Open What "invalid" means

Seven candidate readings in the feedback. Until it is settled, the causes stay itemised here and can be re-grouped in one place once the answer arrives.
